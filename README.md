# Isnād Kids API

Backend for Isnād Kids: parent accounts, child profiles, progress sync, the admin content workflow
(upload → review → publish), and versioned content packs the app downloads for offline use.

**Stack:** [Hono](https://hono.dev) on Cloudflare Workers · D1 + Drizzle · R2 · Queues ·
Better Auth (parents) · Cloudflare Access (admins) · Zod + OpenAPI.

The code follows a **NestJS-style layout**: feature modules with controllers, services (providers),
DTOs, guards and a global exception filter, without NestJS itself, so it stays small and native to Workers.

## Project layout

```
src/
  main.ts                    Worker entry: HTTP + queue consumer          (Nest: main.ts)
  app.module.ts              Registers modules, global middleware, docs   (Nest: AppModule)
  config/env.ts              Typed bindings and variables
  common/
    di/container.ts          Per-request DI container                     (Nest: providers)
    guards/                  AdminGuard, Roles(), ParentGuard              (Nest: guards, @Roles)
    exceptions/              NotFoundException, ConflictException, ...    (Nest: exceptions)
    filters/                 Global error -> JSON                         (Nest: exception filter)
    http/create-router.ts    Router with validation                       (Nest: ValidationPipe)
    http/define-module.ts    defineModule()                               (Nest: @Module)
    security/password.ts     PBKDF2 password hashing (Workers-friendly)
  database/
    schema/                  Drizzle tables
    database.service.ts      Drizzle client provider
  modules/
    <feature>/
      <feature>.module.ts      controllers + providers
      <feature>.controller.ts  routes (OpenAPI-documented)
      <feature>.service.ts     business logic
      dto/                     Zod schemas = validation + OpenAPI + types
migrations/                  SQL generated by drizzle-kit, applied by wrangler
test/                        End-to-end tests running inside the Workers runtime
```

| Module | Routes | Who |
|---|---|---|
| health | `GET /health` | Public |
| auth | `/v1/auth/*` (sign-up, sign-in, sign-out, session) | Parents |
| profiles | `/v1/children` CRUD | Parents |
| progress | `POST/GET /v1/progress/{childId}` | Parents |
| packs | `GET /v1/packs/latest` · `/admin/packs` | Public · admin |
| media | `/admin/media` upload/list/delete · `GET /v1/media/*` | Editors · public |
| content | `/admin/content` CRUD, `/submit`, `/withdraw` | Editors |
| reviews | `/admin/reviews/queue`, decide, history | Reviewers |

Interactive API docs: `http://localhost:8787/docs` · spec: `/openapi.json`.

### Adding a module

1. Create `src/modules/<name>/` with `dto/`, `<name>.service.ts`, `<name>.controller.ts`, `<name>.module.ts`
   (copy `profiles` as a template).
2. Services take the container: `constructor(container: Container) { this.db = container.get(DatabaseService).db }`.
3. Add the module to `APP_MODULES` in `src/app.module.ts`.
4. New tables: add them in `src/database/schema/`, then `npm run db:generate`.

## Content workflow

```
draft ──submit──▶ in_review ──approve──▶ approved ──(admin publishes a pack)──▶ in pack vN
  ▲                  │
  │           request_changes (comment required)
  └── edit ◀── changes_requested
```

- Submitting checks: Islamic items need a `source`; Qur'an Garden items need a `riwayah` (Hafs or Warsh);
  template data must be complete (`listen_along`, `repeat_after_me` and `surah_match` have strict schemas);
  every referenced media file must exist.
- Editing an approved item sends it back to draft. It is left out of new packs until approved again.
- Every decision is stored in `content_reviews` as an audit trail.
- Publishing (`POST /admin/packs`, admin only) queues a build. The consumer writes
  `packs/v<N>/manifest.json` and `packs/latest.json` to R2. The manifest lists every item and file with
  sizes and SHA-256 checksums, so the app downloads only what changed and verifies each file.
- Roles: `editor` (content, media), `reviewer` (decisions), `admin` (everything, publishing, deleting media).


```bash
cp .dev.vars.example .dev.vars
```

```bash
npm run db:migrate:local
```

```bash
npm run db:seed:local
```

```bash
npm run dev
```

In development, admin routes act as `DEV_ADMIN_EMAIL`, or as the email in an `x-dev-admin-email` header.
This only works when `ENVIRONMENT=development`; production always requires Cloudflare Access.

Uploading a file:

```bash
curl -X POST "http://localhost:8787/admin/media?kind=audio&filename=al-ikhlas-1.opus" -H "content-type: audio/ogg" --data-binary @al-ikhlas-1.opus
```

## Deploying to Cloudflare

1. Create the resources and put the D1 `database_id` into `wrangler.jsonc`:

   ```bash
   npx wrangler d1 create isnad-kids
   ```

   ```bash
   npx wrangler r2 bucket create isnad-kids-media
   ```

   ```bash
   npx wrangler queues create isnad-kids-packs
   ```

2. Set the auth secret:

   ```bash
   npx wrangler secret put BETTER_AUTH_SECRET
   ```

3. Set the `vars` in `wrangler.jsonc`: your API domain, media domain, admin portal origin,
   Access team domain and Access application AUD tag.
4. Media: connect a custom domain (for example `media.isnadkids.app`) to the R2 bucket and set
   `MEDIA_PUBLIC_BASE_URL` to it. It is cached at Cloudflare's edge and supports resumable downloads.
5. Cloudflare Access: create a self-hosted application that covers the admin portal and the `/admin/*`
   API paths. Serving both from one hostname avoids cross-site cookie problems.
6. Migrate and deploy:

   ```bash
   npm run db:migrate:remote
   ```

   ```bash
   npm run deploy
   ```

7. Add real admin users:

   ```bash
   npx wrangler d1 execute isnad-kids --remote --command "INSERT INTO admin_users (email, name, role, active, created_at) VALUES ('you@yourdomain.com', 'Your name', 'admin', 1, unixepoch()*1000)"
   ```
